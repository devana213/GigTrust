# GigTrust

**GigTrust** is a cloud-native freelance marketplace prototype designed to demonstrate how a modern application can combine **transaction-safe relational storage**, **polyglot persistence**, **containerized deployment**, **multi-region availability**, **health monitoring**, and **failover routing** on Microsoft Azure.

The project was built as a combined **Database Management Systems (DBMS)** and **Cloud Computing** academic project. The DBMS side focuses on ACID transactions, normalization, concurrency control, escrow workflows, activity logging, telemetry storage, and auditable transaction history. The Cloud Computing side focuses on Docker, Azure Container Registry, Azure Container Apps, Azure App Service, Azure Traffic Manager, health probes, multi-region deployment, and failover.

---

## 1. Project Overview

Freelance marketplaces must handle multiple categories of data and infrastructure requirements at the same time:

- user profiles and gig information
- bids and contracts
- escrow transactions
- concurrent access to shared transactional data
- audit and activity logs
- telemetry generated by deployed services
- regional application availability
- automatic failover during regional service disruption

GigTrust addresses these requirements using a **polyglot database architecture** and a **multi-region Azure deployment**.

### Main idea

The application backend is implemented using **FastAPI** and packaged as a Docker container. The same backend image is deployed in two Azure regions:

- **Central India** — Primary region
- **Korea Central** — Secondary/failover region

Azure Traffic Manager uses **Priority routing** so that requests resolve to the Central India backend during normal operation and switch to Korea Central when the primary endpoint becomes unavailable or is disabled.

The application uses:

- **Azure SQL Database** for structured transactional data
- **Cosmos DB for MongoDB** for activity logs
- **Cosmos DB for Cassandra** for telemetry and scaling-action history

## 2. Project Objectives

The main objectives of GigTrust are:

1. Build a freelance marketplace backend using FastAPI.
2. Maintain transaction consistency for escrow operations.
3. Demonstrate ACID properties and rollback.
4. Handle concurrent transactions safely.
5. Store structured and unstructured operational data using suitable database technologies.
6. Containerize the backend using Docker.
7. Store application images in Azure Container Registry.
8. Deploy the backend in multiple Azure regions.
9. Configure health-based priority routing using Azure Traffic Manager.
10. Demonstrate regional failover and recovery.
11. Store telemetry in Cassandra.
12. Record resource-management decisions such as `NO_ACTION`, `SCALE_UP`, and `REROUTE`.
13. Maintain an auditable history of important system actions.
14. Provide a foundation for future fraud detection and explainable AI modules.

## 5. Database Architecture

GigTrust uses a **polyglot persistence** model. Different types of information are stored in different database systems based on their access characteristics.

### 5.1 Azure SQL Database

Azure SQL is used for strongly structured and transactional data.

Typical relational entities include:

- Users
- Gigs
- Bids
- Contracts
- Escrow transactions
- Payments
- Transaction history

Azure SQL is suitable because marketplace transactions require:

- ACID guarantees
- referential integrity
- constraints
- transaction rollback
- concurrency control
- joins
- reliable financial-state updates

#### Example escrow workflow

```text
Client funds escrow
        ↓
Amount is marked as held
        ↓
Freelancer completes work
        ↓
Client verifies completion
        ↓
Escrow is released
        ↓
Transaction history is updated
```

If any step fails inside a transaction, the database operation can be rolled back so that partial financial updates are not committed.

### 5.2 Cosmos DB for MongoDB

MongoDB is used for flexible operational and activity logging.

Examples:

- user login events
- gig creation events
- bid submission events
- contract actions
- API activity
- fraud-related events
- audit metadata

A document database is suitable because activity records can evolve without requiring rigid relational schema changes.

Example document:

```json
{
  "user_id": 101,
  "event": "BID_SUBMITTED",
  "timestamp": "2026-08-18T10:30:00Z",
  "metadata": {
    "gig_id": 42,
    "bid_amount": 7500
  }
}
```

### 5.3 Cosmos DB for Cassandra

Cassandra is used for time-series-style operational telemetry.

Telemetry data can include:

- CPU utilization
- API latency
- request throughput
- node identifier
- deployment region
- timestamp

The Cassandra design uses a partition based on:

```text
(region, metric_type)
```

and clusters readings by timestamp.

This makes it efficient to retrieve recent metrics for a particular region and metric.

#### Telemetry table

```sql
CREATE TABLE telemetry_readings (
    region        TEXT,
    metric_type   TEXT,
    ts            TIMESTAMP,
    node_id       TEXT,
    value         DOUBLE,
    PRIMARY KEY ((region, metric_type), ts)
) WITH CLUSTERING ORDER BY (ts DESC);
```

#### Scaling actions table

```sql
CREATE TABLE scaling_actions (
    region          TEXT,
    ts              TIMESTAMP,
    action          TEXT,
    trigger_metric  TEXT,
    trigger_value   DOUBLE,
    threshold       DOUBLE,
    PRIMARY KEY (region, ts)
) WITH CLUSTERING ORDER BY (ts DESC);
```

This table provides an audit trail for decisions made by the resource-management agent.

## 6. DBMS Concepts Demonstrated

The project demonstrates several core DBMS concepts.

### ACID Transactions
- **Atomicity** — either all transaction steps succeed or none are committed.
- **Consistency** — database constraints and business rules remain valid.
- **Isolation** — concurrent operations do not corrupt each other's state.
- **Durability** — committed changes remain stored.

### Rollback
If an escrow transaction fails before completion, changes can be rolled back.

### Concurrency Control
The project considers scenarios where multiple operations access the same records concurrently, such as:

```text
Transaction A → releases payment
Transaction B → opens a dispute
```

Proper locking and transaction ordering are required to prevent inconsistent state.

### Deadlock Scenario
A deadlock can occur when two transactions acquire resources in different orders and wait for each other.

The project studies:
- deadlock creation
- deadlock detection
- transaction rollback
- consistent lock ordering as a prevention strategy

### Normalization
The relational model is designed with normalization in mind to reduce redundancy and update anomalies.

The project discusses:
- 1NF
- 2NF
- 3NF
- BCNF
- 4NF where multivalued relationships such as user skills or portfolio items are modeled separately

## 16. SQL Firewall Troubleshooting

The Korea Central deployment initially could not connect to Azure SQL.

The issue was caused by Azure SQL firewall restrictions.

The App Service outbound IP addresses were obtained from Azure Portal and allowed through the SQL server firewall.

After adding the required IP addresses, SQL connectivity from the Korea backend succeeded.

This demonstrates an important cloud networking principle: a service may be running correctly while still being unable to access another Azure service because of network or firewall restrictions.

The system can evaluate telemetry such as:
- CPU utilization
- latency
- throughput

Example normal workload:

```text
Region       : Central India
CPU          : 72.4%
Latency      : 118 ms
Throughput   : 430 RPS
Decision     : NO_ACTION
```

Example high-load workload:

```text
Region       : Central India
CPU          : 88.5%
Latency      : 220 ms

```

When another region is considered healthier, the agent can produce:

```text

Target   : Secondary region
```

Decisions are stored in Cassandra so that the system has an auditable record of why resource-management actions were recommended.

## 20. Failover Test

The project performed a real routing test.

### Normal State

Central India was enabled as Priority 1.

Running:

```powershell
Resolve-DnsName gigtrust-global.trafficmanager.net
```

returned the Central India application hostname.

Conceptually:

```text
gigtrust-global.trafficmanager.net
                  ↓
        Central India backend
```

### Failure Simulation

The Central India Traffic Manager endpoint was temporarily disabled.

After DNS propagation, the same command returned:

```text
gigtrust-korea-gzc3dbaqe8grbnf4.koreacentral-01.azurewebsites.net
```

Conceptually:

```text
gigtrust-global.trafficmanager.net
                  ↓
          Korea Central backend
```

### Recovery

The Central India endpoint was re-enabled.

After the DNS TTL expired and Traffic Manager refreshed its routing decision, DNS resolution returned to the primary Central India endpoint.

Therefore the full sequence was demonstrated:

```text
NORMAL
Central India
      ↓
PRIMARY DISABLED
Korea Central
      ↓
PRIMARY RESTORED
Central India
```

This verified **priority-based multi-region failover and recovery**.

## 21. Why the Traffic Manager URL Is Not Used as a Normal HTTPS Reverse Proxy

Azure Traffic Manager is a **DNS-based routing service**. It does not terminate HTTPS traffic like a reverse proxy.

Therefore `gigtrust-global.trafficmanager.net` returns the hostname of a backend, but the TLS certificate on each backend belongs to that backend's Azure hostname.

For a production single public hostname, a custom domain and suitable TLS configuration would be required.

For the academic demonstration, DNS resolution provides clear proof that Traffic Manager changed the selected region.

Resolved by installing/configuring WSL and Docker Desktop.

### Docker image build failed
Resolved by correcting the Linux base image/repository compatibility required by Microsoft ODBC packages.

### ACR hostname error
The initial registry hostname contained a typo. Correcting the generated secure ACR login server fixed DNS/login failures.

### Azure SQL inaccessible from deployed application
Connectivity was tested at multiple levels:

```text
DNS
→ TCP port 1433
→ ODBC driver
→ SQL login
→ application API
```

### Korea App Service SQL timeout
Resolved by adding required App Service outbound IP addresses to the Azure SQL firewall.

### Second Container Apps environment blocked
Solved by using Azure App Service for Containers for the second region.

### Azure Front Door unavailable
Solved by switching to Azure Traffic Manager.

### Traffic Manager endpoints degraded
Probe routing/host behavior was corrected until both endpoints reported Online.

## 39. Current Limitations

The current project is an academic prototype and has several limitations.

- Traffic Manager is DNS-based rather than a reverse proxy.
- The Traffic Manager hostname is not configured as a shared custom TLS domain.
- Health probing currently uses a database-specific endpoint.
- Resource-management actions are recommendation/simulation oriented rather than fully controlling Azure scaling resources.
- Frontend development is still planned.
- Authentication and production authorization require further hardening.
- Full managed-identity integration is not yet implemented.
- Databases are shared cloud services rather than fully duplicated data stacks per application region.

## 42. Key Viva Points

### Why Azure SQL?
Escrow and marketplace transactions require ACID properties, strong consistency, referential integrity, and transaction support.

### Why MongoDB?
Activity logs are semi-structured and can evolve over time, making a document database appropriate.

### Why Cassandra?
Telemetry is high-volume, time-ordered, write-heavy data. Cassandra's partitioning and clustering model is suitable for this pattern.

### Why Docker?
Docker creates a portable, reproducible application image that can be deployed to different compute platforms.

### Why Azure Container Registry?
It provides private centralized storage for Docker images used by Azure compute services.

### Why two regions?
Multi-region deployment improves availability and demonstrates fault tolerance.

### Why Traffic Manager?
Traffic Manager provides DNS-based global routing and health-aware failover.

### Why Priority routing?
One region acts as primary while the other remains available as a backup.

### Why Central India as primary?
It is geographically appropriate for the primary target environment and was available under the student subscription.

### Why Korea Central for the second region?
Korea Central was one of the regions permitted by the Azure for Students policy.

### Why App Service in Korea instead of Container Apps?
The subscription allowed only one global Container Apps Environment, so App Service provided a practical second-region container host.

### Why not Azure Front Door?
Azure Front Door creation was blocked by the Azure for Students subscription.

### What proves failover worked?
`Resolve-DnsName gigtrust-global.trafficmanager.net` changed from the Central India backend to the Korea Central backend when the primary endpoint was disabled, and returned to Central India after recovery.

## 45. Conclusion

GigTrust demonstrates how a freelance marketplace can be designed using both traditional database principles and modern cloud architecture.

The DBMS layer ensures that important marketplace operations such as escrow transactions maintain consistency and reliability. MongoDB and Cassandra extend the architecture with flexible logging and high-volume telemetry storage.

The cloud layer packages the application as a Docker container, stores it in Azure Container Registry, deploys the same application across Central India and Korea Central, and uses Azure Traffic Manager for priority-based failover.

The successful failover test from Central India to Korea Central and back to Central India demonstrates that the architecture is capable of maintaining service availability during a regional failure scenario.

The project therefore combines:

```text
Database Reliability
        +
Polyglot Persistence
        +
Containerization
        +
Multi-Region Deployment
        +
Health Monitoring
        +
Failover
        +
Telemetry-Based Resource Management
```

into a single cloud-native academic prototype.
